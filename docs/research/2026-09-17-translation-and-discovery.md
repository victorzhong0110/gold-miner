# 自动翻译、跨语言发现与推荐：讨论记录

日期：2026-09-17。性质：设计推理与待验证假设；没有新增产品效果结果。
执行入口：[v0.4 行动计划](../plan/v0.4.md)。

## 1 想法来源与证据边界

| 来源 | 带来的问题或启发 | 能支持什么 |
|---|---|---|
| 发起人此前的需求讨论 | 没有明确目标也能遇见好项目；原页面自然探索；中英双向搜索；共享翻译；零公共模型补贴 | 已确认的产品目标和约束，不是需求规模证明 |
| 发起人转述的 X 讨论 | “中文 GitHub 遍地宝藏”下有人表示看不懂 | 问题线索；原帖链接和截图尚未提供，不推算用户数量 |
| [Claude 的 v0.3 评审](../reviews/2026-09-17-v0.3-review.md) | 脚本先行、强对照、独立评估材料、可追溯记录、名称竞争 | 值得采纳的方法；评审中的市场判断和实验门槛仍可修订 |
| [EhViewer 研究](ehviewer-cross-language-search.md) | 用户语言与原始检索标识之间的映射 | 借鉴概念映射；没有证明可直接复用通用跨语言搜索引擎 |
| 发起人本轮问题一 | 如果 AI 自动翻译电脑上看到的一切，黄金矿工会不会被替代？ | 用作产品压力测试的未来假设，不是已经普及的能力声明 |
| 发起人本轮问题二 | TikTok 的推荐算法是否适用？ | 引出兴趣学习、探索多样性和反馈含义的讨论 |
| 下列官方资料 | 当前翻译功能与推荐机制的公开描述 | 支持功能或机制存在，不证明黄金矿工有效 |

官方资料于 2026-09-17 查阅：

- [Chrome 翻译设置](https://support.google.com/chrome/answer/173424?hl=en)：可配置自动翻译指定语言；不能据此声称电脑上一切内容都已无感翻译。
- [沉浸式翻译使用说明](https://immersivetranslate.com/en/docs/usage/)：网页双语显示、只显示译文等功能，可作为候选阅读基线；尚未进行 GitHub 体验对照。
- [TikTok 推荐机制公开说明](https://newsroom.tiktok.com/how-tiktok-recommends-videos-for-you)：2020 年发布的概述，提及互动、内容信息、兴趣反馈与内容多样性；不是当前完整模型、权重或可直接移植的代码。

## 2 在“翻译已经很好”的前提下检验价值

| 假设中的能力 | 对黄金矿工的影响 | 后续验证 |
|---|---|---|
| 用户看到的内容都能准确、及时地翻译 | README、讨论、注释的自建翻译大幅失去必要性；缓存价值取决于实际费用和等待节省 | 先试现成阅读工具，仅对观察到的缺口补充能力 |
| 同时能自动处理跨语言输入和检索 | 简单译词、查询扩展的独立价值也可能下降 | E1 与简单译词、联网 AI 比较 |
| 同时理解兴趣并主动发现合适项目 | 可能覆盖黄金矿工的大部分功能 | E2、E7 与实际可用的强对照比较，不承诺不会被替代 |

显示层翻译不会自动改变未进入结果的候选；但更广泛的 AI 检索与推荐可以继续覆盖这些能力。专做 GitHub、本地偏好、可追溯来源都是待验证的产品选择，不能当作不可替代性的证明。

当前执行原则：给对照组同样好的翻译，再测额外的发现收益。项目短期不以盈利为目的；若现成工具足够好，应减少重复开发，必要时缩小或停止独立产品。

## 3 两条独立验证路径

1. 有明确需求时：是否找到了原路径漏掉、符合用途和必要条件的项目。见 [E1](../../experiments/E1-cross-language-search/protocol.md)。
2. 没有明确需求时：是否遇见以前不知道、愿意进一步使用、学习或探索的项目。见 [E2](../../experiments/E2-open-ended-discovery/protocol.md)。

E1 的某种复杂方法没有增益，不等于 E2 必然无效。通用 AI 能回答一个问题，也不代表用户一定会想到问那个问题。反过来，人工挑选的候选很吸引人，也不证明自动推荐已有效。

“仅中文 README 占比”可用于描述材料，不能作为项目生死门槛：少数冷门项目可能有用；双语 README 也可能遗漏另一语言文档中的具体能力。第一轮仍聚焦仓库与 README，功能、示例和讨论级发现仅保留扩展方向。

## 4 借鉴推荐机制时需要重新定义反馈

以下为本项目提出的假设和设计建议，尚未实测：

| 观测 | 可能的解释 | 第一轮做法 |
|---|---|---|
| 停留很久 | 感兴趣、内容难懂、配置失败、切到别的窗口 | 只作辅助记录，不作为首要优化目标 |
| 很快离开 | 不适合，也可能已经找到需要的信息 | 不直接作为负反馈 |
| Star 或收藏 | 稍后读、支持作者、实际兴趣 | 不等同于实际使用，也不自动扩大同类推荐 |
| 跳过外语项目 | 不感兴趣，也可能只是看不懂 | 先提供可比的阅读条件，再解释偏好 |
| 明确表示值得试用或学习 | 有具体用途或学习点 | 保存用户理由；后续有机会再核对行动 |

候选的文档语言不应默认成为推荐边界。展示遵循用户阅读语言；编程语言、平台和部署条件作为不同维度处理。

早期先使用内容特征、明确兴趣和当前仓库上下文，不预设需要训练大型推荐模型。每次少量候选，允许关闭、减少某类内容与重置偏好；保留可解释的新方向。stars 与历史浏览仅在用户主动启用后使用，默认推荐不等于默认上传历史。

## 5 可共享的不只有长篇译文

建议先试“项目发现条目”：中英文用途、实际检索别名、适合的探索类型、能力与限制的原文依据、来源版本和未知项。它可以帮助候选检索、快速理解与继续探索；详细译文仍按需生成。

与 EhViewer 的联系是概念与别名映射，不是复制其领域词库。共享条目只作为补充；没有条目的项目仍须有开放检索路径。公共贡献只覆盖允许分享的公开内容，个人密钥、查询、偏好、浏览历史和私有内容不进入包。具体公共分发方式在 E5 之后决定。

该条目库不会自动让 GitHub 原生搜索索引所有别名；其直接效果先限于黄金矿工自己的检索与呈现。项目自身的多语言可发现性另由 E8 验证。

## 6 自然度从安装和配置开始

自备 API 保留。首次使用需要记录选择服务、配置、等待、失败和退出，不能只从配置成功后开始计算体验。

建议验证：先看已有的公开资料或无需新模型调用的结果，产生新模型请求时再引导配置；服务预设减少输入，高级配置保留。GitHub 凭据只有在实际配额或功能需要时再引入。没有凭据的体验能否成立，必须实测，不能预先承诺。

## 7 对 Claude 评审的处理

| 建议 | v0.4 处理 |
|---|---|
| 小脚本先验、真实来源、强对照、开发与评估分离 | 采纳 |
| H1 是唯一生死假设，全部扩展工作由 E1 决定 | 改为搜索与无目标发现分别判断；最小扩展按对应证据进入 |
| README 仅中文比例过低就取消一个方向 | 不采用；分方向记录实际收益与反馈缺口 |
| 由项目介绍反推查询作为独立真实需求 | 只作已知目标诊断，并披露答案条件化偏差；另写开放任务 |
| 种子命中率是总体召回下限 | 改为已知目标命中率；不推断总体召回或其下限 |
| 只将工具和库计为有效发现 | 加入符合用户兴趣的学习实现、示例与教程 |
| 增强组优于一次搜索即可归因于跨语言 | 增加相同查询预算与搜索字段的同语言对照 |
| 名称竞争意味着必须先改名 | 沿用已选工作名；补双语用途信息后重测，不以改名阻塞实验 |
| 默认要求第二套 GitHub 凭据 | 先测实际限制；配置负担纳入 E4/E6 |
| 模型服务可替换 | 采纳架构原则；不承诺首轮接完全部供应商 |

本记录保留不同意见及其来源。历史评审和 E8 首次探测保持原文，以便日后比较哪些推断获得了支持。
