# E1 跨语言搜索：小样本验证协议 v0.4

修订：2026-09-17。状态：方案已整理，尚未运行；评估题、预算、提示词与模型配置仍待执行工作包固定。
执行入口：[v0.4](../../docs/plan/v0.4.md)。本版替代原协议的 H0 门槛、方法归因和“召回下限”表述；历史版本保留在 Git 历史中。

## 0 问题和范围

- 固定需求下，跨语言路径是否带来确实合适的新候选？
- 收益来自语言切换、一般查询扩展，还是搜索范围/预算变化？
- 简单译词是否已经够用，复杂改写的成本是否值得？
- 中文找英文项目与英文找中文项目分别怎样？

本实验用脚本与人工核对，不需要完整扩展。它不代替 [E2 无目标发现](../E2-open-ended-discovery/protocol.md)，也不能评价安装与原页面自然度。E2a 和翻译基线检查可以独立进行。

## 1 先做小范围来源检查

选少量来源可核对的中英文仓库，记录默认字段、显式 README 查询、短词/长短语的实际返回。已知仓库的用途短语只作接口诊断，不作为独立真实需求。

保留原始查询、实际字段、时间、结果窗口、限流/超时和目标是否出现。不要由少量中文短语的失败推断整个中文项目空间不可检索；区分索引、分词、查询表达、窗口截断和接口失败。

文档语言人工核对并保留位置，按所检查的具体材料标记；不要把代码 language 筛选当作文档语言。存在英文 README 不等于所有能力都有英文说明。无需先统计全站中文比例，也不以 stars 下限排除冷门项目。

## 2 材料与冻结

### 开放任务

在看结果前写需求和硬条件，覆盖工具、冷门用途、学习实现；两种查询语言都包含常见术语、歧义、否定或长需求。来源可为发起人的真实想法或明确标记的合成任务，不能将合成内容称为用户需求证据。

首轮建议 8 条开放评估任务（每方向 4 条），用于低成本探路；不足以估计总体效果。开发仍使用现有 dev 题，评估不从开发题改写。

### 已知目标诊断

首轮建议 8 条已知目标题（每方向 4 条），从多个来源取仓库，如项目公开文档、社区介绍和主题清单。HelloGitHub 可以提供线索，不能是唯一来源。记录来源、发现日期、stars、用途与能力证据，包含低热度材料。

由项目介绍反推的查询只作已知目标题，明确标注这种偏差。开放任务的作者不应先看种子答案。人工挑选、同一人构题和判断的情况照实披露；未实现盲测时不能写“盲测完成”。

### 冻结方法

运行评估前提交任务、种子、提示词/词表、字段配置、排序、预算、模型标识和运行说明。查询文件中的冻结提交先留空；在后续记录提交或运行清单中填写已存在的提交 SHA，避免要求文件包含自身提交 SHA。

运行后不改本批材料。修复或调参后另开批次，旧失败保留。样本数量是本轮默认建议，不是统计保证；执行者可在首次运行前调整并说明原因，无需发起人逐项审批技术参数。

## 3 方法组

保留原 A/B/C/D 名称，增加 M 同语言对照。所有检索方法只接受同样的原始需求与必要条件，不给某一组单独增加语义信息。

| 组 | 做法 | 目的 |
|---|---|---|
| A 原生 | 原查询，默认仓库搜索，1 次请求 | 用户原来操作的现实对照 |
| B 简单译词 | 原查询加另一语言的忠实查询翻译，共最多 2 次 | 看简单办法是否足够；记录翻译来自人工、固定词表还是模型 |
| C 跨语言扩展 | 原查询加最多 3 个查询；其中两个使用另一语言，共最多 4 次 | 测跨语言扩展 |
| M 同语言扩展 | 原查询加最多 3 个同语言改写，共最多 4 次 | 分离更多查询与语言切换的效果 |
| D 联网 AI | 同需求与条件，请实际可用的联网助手返回真实仓库并说明依据 | 强工具对照；记录版本、日期、耗时和可见调用/费用，不假装内部预算已知 |

C 与 M 的查询生成各最多 1 次模型请求，模型、可见上下文、输出限制与排序方法保持一致；主要变化只有允许使用的语言。重复查询去重，按实际请求数报告；不能为了填满预算故意添加无关查询。

C/M 第一次比较使用完全相同的搜索字段设置。README 扩展作为另一轮配对诊断：两组同时启用相同字段，而不是只在 C 结果少时扩大范围。主结果将“默认字段”和“增加 README 字段”分开报告。

首轮每条 GitHub 查询取前 30 条，不额外翻页；合并后固定排序和截断为前 30。C/M 共用排序，原始位置与各路候选都保留。热度只作辅助，不成为低 stars 项目的排除条件。若排序采用命中次数，应说明这会受近义查询重复影响。

D 可先在运行前选定的少量代表任务上试用，以控制人工与模型成本；结果只适用于这些配对任务，不与全量任务平均数混用。D 的联网行为不可完全控制，比较的是实际工具体验，不是严格等计算量算法实验。

## 4 判定与翻译控制

所有组候选先规范地址、去重，合并后隐藏组名做内容核对；原始排名保留。首轮统一检查各组前 5 个候选，预算相同；后续扩大到前 10 时另开批次。用于检索诊断的已知目标命中@30可以另算，不要求读完 30 个。

所有候选采用同一阅读语言和翻译设置；关键用途与限制回查原文。不让 C 独享更好的翻译或项目介绍。

区分：

- 用途：符合 / 部分符合 / 不符合。
- 硬条件：满足 / 冲突 / 未知；未知不能算满足。
- 类型：工具 / 库 / 学习实现或示例 / 教程 / 清单 / 镜像 / 其他。
- 对评价者是否新颖：是 / 否 / 未知。
- 值得继续看的理由：原话或明确标记的技术判断。
- 项目与子能力：同仓库不同能力可另记线索，但项目数量按规范仓库去重。

学习材料只有与学习目的相符才算合适，不因类型而自动排除或自动通过。技术判断和真实使用者价值判断分别记录。

## 5 记录格式

计划使用 JSONL，尚未生成运行数据：

- 运行：run_id、batch、materials_commit、prompt_version、model、reading_setup、method、field_config、requested_budget、actual_requests、started_at、elapsed、errors。
- 候选：task_id、query_original、query_variant、variant_lang、query_source、repo、source_url、rank_before_merge、rank_after_merge、matched_fields、document_lang、evidence_location、fetched_at。
- 判断：task_id、repo、purpose_fit、hard_conditions、kind、novel_to_judge、worth_following、reason、judge、judged_at。
- 成本：GitHub 请求、模型请求、失败与重试、可获取的 token/费用、缓存命中、人工核对时间。未知费用写未知。

拿不到匹配字段就记 unknown，不根据标题相似度补造。仓库不存在、迁移、接口限流或超时与不相关结果分开统计。记录只包含允许公开的任务和来源；不导出密钥、完整认证头或私人浏览历史。

## 6 指标与解释

| 观察项 | 定义 | 不能声称什么 |
|---|---|---|
| 已知目标命中@30 | 种子任务中指定目标进入该组前 30 的比例 | 不是全体相关仓库的召回率，也不是总体召回下限 |
| 各组独有合适候选 | 在相同检查窗口内仅该组发现、用途符合、没有已知硬冲突的仓库；条件未知单列 | 不表示别的路径永远找不到 |
| 有价值的新发现 | 原本不知道、能说明用途或学习点、愿意继续探索；保留判断者身份 | 不能只按点击或模型打分计数 |
| 前 K 适合度 | 报用途匹配，以及条件已满足/未知的分项 | 不把用途匹配当成可直接使用 |
| 硬条件问题 | 分开记排序中出现冲突、以及展示错误宣称满足 | 出现在结果里不自动等于误导用户 |
| 成本与等待 | 实际请求、耗时、失败、人工投入和可见费用 | 不假设固定订阅等于无限免费 |

A→C 衡量整体辅助效果；M→C 才更接近相同预算下的语言扩展贡献。B→C 判断复杂程度是否值得。差异仍受查询质量与排序影响，结论应保持在本批材料范围内。

## 7 继续、缩小与暂停

不沿用“中文 README 小于 3% 就取消一个方向”的规则，也不以任意小样本百分点作为产品成功证明。

- 新评估任务中出现可解释、可复核的额外好结果，才支持继续一轮；同时报告本方案漏掉的好结果。
- C 与 B 相近时优先简单方案；C 与 M 相近时不宣传跨语言独有收益。
- C/M 差异仅由字段、请求数、翻译条件不一致造成时先修实验，不能作效果结论。
- 没有增益时定位接口、构题和检索策略问题；修正可解释问题后用新批次复查，不反复调到旧题通过。
- 强对照已同样好用时，讨论缩小功能或停止该路径。
- E1 结论只影响相应搜索投入；E2 独立报告。

## 8 与 E9 的关系

E9 比较纯词表、纯 AI、词表加 AI。B 若由模型生成翻译，就不属于纯词表组。每组标明真实处理方法，配平后端字段、候选预算和排序；未收录词、歧义和否定条件需要保留。

可以复用 E1 记录格式与冻结题集做配对诊断，但若已经用 E1 结果调过词表或提示词，就需要新评估批次才能再声称未见题上的增益。
