# 黄金矿工 产品验证与开发计划 v0.3

本文件自 README 原文迁出（2026-09-17），正文未改动。后续版本另起文件，不覆盖本文。

版本 0.3 \| 2026 年 9 月 16 日 \| 补充项目自身的多语言可发现性

## 1 已确认的产品方向

黄金矿工让用户用自己的语言发现、阅读和探索 GitHub 上的项目。首要体验是没有明确目标也能遇见值得看的项目，同时支持跨语言主动搜索。衡量价值的依据是真实发现效果、探索是否自然，以及阅读能否帮助用户理解项目。

本版在 0.2 版基础上增加项目自身的多语言可发现性要求，详见第 11 节，并补充发布材料与实验 E8。当前完成的是方案确认与文档更新；扩展开发、真实模型调用和用户实验尚未启动。

| **已确认事项** | **决定**                                                                                   |
|----------------|--------------------------------------------------------------------------------------------|
| 载体与语言     | 先做 Chrome 扩展，在 GitHub 原页面内工作；首轮中英文双向支持。                             |
| 发现与搜索     | 默认开启个性化推荐；英文检索应有机会找到只有中文说明的项目，反向同样成立。                 |
| 内容偏好       | 覆盖可直接使用的小工具、冷门问题解决方案、可学习的代码实现等；用户能自行选择兴趣。         |
| 阅读体验       | 忠实翻译，可查看原文；允许首次加载和逐段呈现。初学者解释后置。                             |
| 个性化信息     | 兴趣选择与当前项目为基础；stars 和 GitHub 浏览记录可由用户选择启用。                       |
| 费用边界       | 项目不为他人使用承担费用；用户自备 API。发起人的个人 API 可用于自己试用。                  |
| 翻译积累       | 已有译文应尽量复用，并探索把可共享内容提供给其他使用者。                                   |
| 开源与验证     | 源码开源；发起人愿意首先试用，后续可在社交媒体推广。短期不以盈利为目标。                   |
| 项目自身可发现 | 黄金矿工也应能被不同语言的用户直接搜索找到；首轮中英文，后续扩展更多语言，并验证真实入口。 |

### 首轮交付边界

实现发现、搜索、关键内容阅读、讨论阅读与继续探索。独立发现入口、发布 issue、提交修改和初学者教学说明留待后续。首先验证一个可实际安装使用的最小扩展，现有演示站点不作为核心产品或效果证据。

## 2 第一版体验与验收场景

### 没有明确目标时也能开始

用户在熟悉的 GitHub 页面浏览，依据选定兴趣与当前仓库看到少量相关但有差异的项目。推荐理由直接说明它解决什么问题、为什么与当前兴趣有关，以及需要什么使用条件。用户不必先写一段完整需求，才有内容可看。

推荐默认出现，但应控制占用空间，允许关闭、减少某类内容和改变兴趣。小工具更重视运行与安装条件；学习型项目更重视实现思路和代码价值。不要用同一套“开箱即用”标准排除所有学习型项目。

### 用自己的语言搜索另一种语言的项目

用户用英文搜索 clipboard history，即使某项目的用途只在中文 README 中描述为剪贴板历史，也应有机会进入候选。扩展应补充跨语言候选获取、合并和排序，再用用户偏好的语言呈现。用户不必自己翻译关键词或学会 GitHub 搜索语法。

这是一项验收目标，不是当前已经实现的覆盖承诺。搜索不能只检查已被翻译过或人工挑选过的仓库。没有共享译文的项目仍需有发现路径，并允许在被阅读时生成译文。

### 进入项目后保持阅读连续

先处理项目说明与 README，按实际阅读再处理文档、issue 讨论和代码注释。保留标题、链接、列表、代码块与评论关系；译文与对应原文可切换。代码标识符、命令和可执行内容按原样呈现，翻译针对说明性文字与注释。

首次没有译文时，允许短暂加载和逐段显示；已有缓存时优先复用。机器译文保留可识别的来源与版本信息，用户需要时能检查依据。翻译失败应明确显示状态，不把残缺内容包装为完整翻译。

### 从一个项目继续探索

用户可以沿类似用途、不同实现、更易部署或新的兴趣方向继续浏览。推荐应记住用户刚排除的项目与当前兴趣，支持返回上一条探索路径。第一版以页面交互为主，不要求先实现独立聊天助手。

| **首轮场景** | **需要观察到的结果**                               |
|--------------|----------------------------------------------------|
| 随意逛       | 用户愿意打开此前不认识的项目，并能说出具体吸引点。 |
| 主动搜       | 另一种语言的相关项目进入结果，满足用途与必要条件。 |
| 读内容       | 用户能够准确理解作者原意，并辨认关键限制。         |
| 接着逛       | 能够沿兴趣继续或返回，不反复丢失方向与偏好。       |

## 3 发现系统需要解决的问题

### 候选必须来自真实来源

第一阶段建议按用户当前操作获取真实候选，再逐步积累来源记录。检索词可以在用户端通过个人 API 改写为中英文表达；原始查询、扩展查询与返回仓库需要记录，便于判断新结果从哪里来。模型生成的仓库名称不能直接当成真实项目，必须核对来源。

GitHub 仓库搜索默认检查名称、描述与 topics；README 内容需使用 in:readme。language 筛选指代码语言，不能当成文档语言。黄金矿工应在内部处理这些差别，避免把额外语法负担交给用户。相关官方说明见第 10 节。

| **问题**     | **首轮处理原则**                                         | **仍需验证**                                     |
|--------------|----------------------------------------------------------|--------------------------------------------------|
| 跨语言遗漏   | 结合原语言和另一语言的查询；保留仅另一语言找到的候选。   | 提升是否超出简单译词搜索，是否损害相关性。       |
| 重复与伪候选 | 区分实际工具、项目清单、镜像和分支，解析规范仓库地址。   | 是否重复推荐同一项目，是否将教程当成可用软件。   |
| 偏好与新颖性 | 用途匹配优先，保留少量可解释的不同方向；用户可调整兴趣。 | 是否反复推熟悉项目，是否只剩越来越窄的内容。     |
| 硬条件判断   | 对系统、部署、联网等条件区分满足、冲突与未知。           | 能否避免把缺少说明当成已经满足。                 |
| 推荐质量     | 保留为什么推荐、能力依据和限制；热度只作为辅助信息。     | 冷门项目是否确实值得看，热门项目是否被不当排除。 |
| 数据新鲜度   | 保留抓取时间、内容版本及失效状态，按需更新。             | 迁移、归档和能力变更能否及时反映。               |

### 个性化的最小实现

基础输入是用户选择的兴趣、当前仓库，以及用户主动表达的喜欢或不感兴趣。stars 与 GitHub 浏览记录属于可选输入，提供查看、关闭和重置方式。推荐默认开启，不代表默认上传浏览历史。初版偏好与行为状态优先保存在本地。

“默认开启个性化”仍需控制调用次数：相同页面与相同兴趣优先复用已有结果，限制自动刷新。不要把每次滚动或页面细微变动都转成模型请求。模型选择、查询预算和排序方法由技术实验确定。

## 4 翻译复用与费用边界

### 按内容和版本积累译文

翻译以文档段落或讨论片段为单位，提供足够上下文以保持术语一致；无需先翻译整个仓库。复用时检查原文版本、目标语言及相关翻译配置。原文或上下文变化后更新受影响部分，避免旧译文看起来像当前说明。

| **译文记录** | **最低需要保存的信息**                                       |
|--------------|--------------------------------------------------------------|
| 定位与来源   | 规范仓库地址、文件或评论位置、来源链接和读取时间。           |
| 版本与内容   | 原文内容校验值、段落边界、必要上下文及目标语言。             |
| 翻译信息     | 译文、生成时间、模型与配置版本，以及机器生成或人工修订状态。 |
| 质量与共享   | 检查结果、纠错记录、可复用范围与原内容的许可信息。           |

### 首轮共享从可交换的数据开始

建议先实现本地缓存和可导入导出的译文包，用第二个浏览器配置或另一位使用者验证确实能复用。随后以版本化静态数据包提供小规模公共内容，审核贡献后发布。这样无需先建设持续运行的公共模型代理或实时数据库。

用户主动开启贡献后，只提交许可允许复用的公开内容及必要来源信息。个人 API 密钥、搜索词、stars、浏览历史和私有仓库内容不进入公共译文包。人工修订应保留版本，避免不可信修改直接替换所有人的结果。

公共存储与下载资源也存在容量和流量限制。具体托管方案需核对实际免费额度和使用规则；超出零现金支出边界时，缩小数据范围、暂停同步或改用用户自行托管，不默认改成由项目付费。

### 模型调用费用各自承担

扩展使用用户自己的 API，模型调用不经过项目提供的公共推理服务。共享译文优先复用，缺失部分由当前使用者决定是否生成。共享服务不保管模型密钥，也不以发起人的账号为其他人提供计算额度。

为减少重复调用，设置缓存、任务合并、有限并发、单次输出限制、重试上限及可取消任务。使用者应能暂停自动生成，看到本次操作的调用情况。自备 API 并不意味着允许无限制后台处理。

### 共享不会自动解决的事情

复用不能消除首次生成、质量检查和持续更新的成本，也不能保证所有仓库都有译文。错误翻译同样可能被放大，因此来源追溯、版本失效和纠错机制是共享功能的一部分。跨语言检索还必须覆盖没有共享译文的项目。

## 5 实验设计与比较方法

先以发起人的实际使用开展小实验，不沿用 0.1 版预设的大规模招募数量。新用户和英文使用者在后续能实际接触到时再加入。发起人的体验能指导开发，但不能代表所有语言或人群。

| **实验**      | **验证问题与做法**                                                                               | **保留的证据**                                             |
|---------------|--------------------------------------------------------------------------------------------------|------------------------------------------------------------|
| E1 跨语言搜索 | 在查看结果前固定中英文需求，比较原生搜索、译词搜索与黄金矿工。开发题与新评估题分开。             | 候选来源、仅单一路径找到的项目、适合度、漏掉的好结果。     |
| E2 无目标发现 | 用户按平时习惯逛 GitHub，再观察带推荐的浏览。平衡不同内容和顺序，记录原本认识的项目。            | 实际打开、值得继续看的原因、兴趣调整与重复推荐。           |
| E3 忠实翻译   | 对真实 README、讨论和注释比较普通网页翻译与方案译文，核对术语、否定、限制和格式。                | 错误原文位置、是否改变理解、翻译与解释是否混淆。           |
| E4 探索自然度 | 安装后进行真实浏览、阅读、返回与继续探索；观察自动推荐与逐段翻译是否打断操作。                   | 卡住或误操作的位置、等待、布局变化与用户原话。             |
| E5 译文复用   | 在另一浏览器环境导入已有译文，再修改部分源文，检查缓存命中、失效和增量更新。                     | 是否减少重复请求、是否误用旧译文、贡献数据是否干净。       |
| E6 API 与费用 | 验证个人密钥直连、身份隔离、用量查询、限流、取消与有限重试，不使用公共模型账号。                 | 实际调用记录、耗时、额度变化、失败与恢复行为。             |
| E7 持续使用   | 建议试用约一周，区分打开、阅读、安装或学习代码；记录出现新需求后是否再次使用。                   | 具体用途、继续或放弃的原因，以及未观察到的结果。           |
| E8 搜到本项目 | 发布后，以各支持语言的名称和功能词，在 GitHub 默认搜索及普通搜索引擎查找官方入口；详见第 11 节。 | 查询原文、语言、入口、日期、检查范围、是否找到及结果位置。 |

### 比较对象与公平条件

原生 GitHub 加普通网页翻译是必要对照；支持联网的通用 AI 也应尝试相同的开放探索和搜索任务。单独比较译词扩展，可判断收益是否需要更复杂的机制。不同方法使用相近时间与候选检查预算，保留失败和未知。

同题候选评价可以合并去重并隐藏方法名称，但用户第二次看到答案后的速度不能用作优势证据。固定候选池能比较排序或交互，开放获取才检验覆盖。技术脚本通过不等于用户觉得自然；后者需要真实使用反馈。

## 6 评价口径与继续条件

先记录可以复查的事实，再讨论是否值得继续。小样本以具体案例和失败原因判断方向，不用点击率或模型自评分制造确定性。以下是首轮的观察口径，不是已经得到的结果。

| **观察项**     | **定义与记录方式**                                                                                           |
|----------------|--------------------------------------------------------------------------------------------------------------|
| 有价值的新发现 | 用户确认此前不知道，并说得出用途、学习点或想继续看的原因。记录具体仓库，不能只计点击。                       |
| 候选适合度     | 分别核对用途与必要条件，标记满足、冲突、未知。学习项目和可直接使用的工具分别评价。                           |
| 跨语言增益     | 在相同预算下，记录只有某一路径找到且确实适合的项目；双方独有的好结果都保留。未知全量结果时不声称总体召回率。 |
| 翻译可靠性     | 记录改变作者原意、遗漏限制、误译否定或破坏命令的错误。检查长讨论中指代和回复关系，而不只看文字流畅。         |
| 探索自然度     | 观察用户需要多少次额外操作、是否被推荐或等待打断、能否返回和继续。较长停留既可能有兴趣，也可能是看不懂。     |
| 费用与复用     | 记录成功、失败和重试请求，用量变化、等待时间与有效缓存命中。旧译文误命中不算收益。                           |
| 持续价值       | 区分收藏、阅读、实际安装、解决问题或学习代码；后续有相关机会时是否主动回来使用。                             |

### 发起人首轮试用

建议至少覆盖三次不同情境：一次随意浏览、一次沿某类兴趣继续探索、一次带具体需求的跨语言搜索。每次记录发现和放弃的项目、阅读误解以及卡住的位置；随后观察约一周内是否实际使用其中的项目。次数与时长可按真实习惯调整。

中英文检索都可先做技术检查，但英语使用者的理解与自然度需要相应使用者反馈。没有获得这类反馈时，应明确保留空白，不能用发起人的体验替代。

### 继续、缩小与暂停

- 继续：不同场景下出现具体的新发现，用户愿意阅读或尝试，且操作负担与个人调用费用可接受。先修复已观察到的问题，再扩展样本。

- 缩小：若跨语言搜索有效但推荐打扰，先保留搜索；若普通网页翻译足够，减少自建翻译范围，把精力放在发现与阅读连续性。

- 暂停或改方向：收益持续只能在预选仓库或开发题上出现，真实浏览没有增益，或强对照已同样好用。保留失败记录，重新检查问题是否成立。

## 7 分阶段开发与交付

下面是后续开发顺序。当前只完成第 0 阶段的需求与计划整理，未开始实现扩展；这些阶段不应被理解为已经执行。

| **阶段**       | **交付内容**                                                                         | **进入下一阶段的依据**                                  |
|----------------|--------------------------------------------------------------------------------------|---------------------------------------------------------|
| 0 需求与计划   | 确认产品边界、个人 API、零公共补贴、实验方法和未知问题。                             | 本版文档可作为后续实现依据。                            |
| 1 最小贯通实验 | 接入个人 MiniMax；从真实搜索得到一个跨语言候选，在 GitHub 原页面阅读并缓存一段译文。 | 直连、数据来源与用量可核对；没有公共推理服务依赖。      |
| 2 核心探索体验 | 补全兴趣选择、默认推荐、跨语言结果合并、阅读切换、返回路径与失效处理。               | 能连续完成随意逛、主动搜、读内容、接着逛四种场景。      |
| 3 复用与试用包 | 导出导入译文包、验证跨环境复用；整理源码、安装说明、多语言项目介绍与搜索验收记录。   | 其他使用者可用自己的 API 安装试用，私有信息不随包共享。 |
| 4 实际使用反馈 | 发起人试用并修复障碍；发布后检查不同语言能否搜到项目，再招募自愿使用者并决定推广。   | 获得真实发现、误解、费用和重复使用记录。                |

### 技术方案由最小实验收敛

建议采用 Chrome 扩展：页面脚本处理 GitHub 展示，后台处理个人 API 请求和任务队列，本地保存偏好与译文缓存。搜索与来源获取独立于翻译缓存；API 适配与页面渲染分离，以便更换模型和修复 GitHub 页面变化。具体框架、组件库与排序策略不再要求发起人逐项选择。

先验证 Chrome 请求权限、GitHub 页面导航与动态内容、搜索接口可用额度以及实际 API 返回格式。若公共接口额度不足，再评估用户自备 GitHub 凭据；不预先要求每个人额外配置一组凭据。

### 验证与交付要求
