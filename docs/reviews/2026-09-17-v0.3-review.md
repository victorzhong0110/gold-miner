## 0 总评

v0.3 的长处：状态诚实（反复写明未实现、未验证）、边界清楚（零公共补贴、自备 API、代码许可与数据许可分开）、有实验意识（E1–E9、H1–H8、继续／缩小／暂停条件）。研究记录里把 EhViewer 的 Apache-2.0 代码许可和 EhTagTranslator 的 CC BY-NC-SA 词库许可分开处理，这个纪律值得保持。

两项计划外的风险比计划内任何一项都大：

1. 项目名称在 GitHub 搜索中已被占满，第 11 节的 E8 验收在当前名称下几乎必败（第 1 节）。
2. 开发顺序把治理（译文包、共享、费用边界）排在生死假设 H1 之前；H1 不需要扩展就能验证，且如果 H1 不成立，产品会收缩到已有工具覆盖的区域（第 3 节）。

## 1 证据：项目自身在 GitHub 搜索中的位置

2026-09-17 用 GitHub REST Search API（等价于 GitHub 默认仓库搜索的字段范围：名称、简介、topics）探测，完整记录见 [E8 探测记录](../../experiments/E8-discoverability/2026-09-17-probe.md)。要点：

- `gold miner`：1,047 个结果，第一名 [xitu/gold-miner](https://github.com/xitu/gold-miner)（34,340 stars，4,983 forks，简介"掘金翻译计划……英译中技术社区"）。同名、同赛道。本仓库不在前 20。
- `黄金矿工`：130 个结果，前 8 名全部是黄金矿工游戏（cocos、C++、PIXI.JS、egret 实现）。本仓库不在结果中。
- `Gold Miner GitHub`：19 个结果，本仓库不在前 20。`黄金矿工 GitHub`：0 个结果。
- 四条用途词查询（`GitHub 跨语言搜索`、`GitHub cross-language discovery`、`跨语言 GitHub 项目发现`、`cross-language GitHub project discovery`）全部 0 个结果。

两点解读：

- 名称维度：名称加用途的查询会被 xitu 与游戏占据；这不是排名问题，是词场被占。
- 用途维度：0 个结果说明这个词场是空的。只要名称不与他人冲突，简介和 topics 写对，用途词查询很容易被本项目占住。
- 协议缺陷：第 11 节的样例查询带有"GitHub"一词。GitHub 站内搜索把它当作普通词项，要求仓库名称／简介／topics 里出现 github，所以带"GitHub"的查询在站内几乎必然为 0。样例查询应分两组：站内搜索去掉"GitHub"，普通搜索引擎保留。E8 模板已按此修改。

结论：名称问题应在写第一行代码前决定，此时沉没成本为零。见 [决策 0001](../decisions/0001-project-name.md)。

## 3 方法论

### 3.1 H1 是生死假设，用最便宜的方式先验

H1（语言造成遗漏）决定产品的独有价值。若 H1 不成立，产品收缩为"忠实翻译阅读"，而这一块沉浸式翻译已经在做：任意网页含 GitHub、段落级双语对照、支持用户配置自己的模型服务与 key。第 6 节"缩小"条件里"若普通网页翻译足够，减少自建翻译范围"实际上指向的就是这个结果。

验证 H1 不需要 Chrome 扩展。一个脚本即可：原始查询 → 中英改写 → GitHub Search API → 合并去重 → 记录每个候选来自哪条路径。协议见 [E1](../../experiments/E1-cross-language-search/protocol.md)。

建议：第 7 节"1 最小贯通实验"拆为两步。
- 1a 脚本验 H1：不写扩展；产出 E1 首轮记录与召回下限。预计 1–2 个工程人日。
- 1b 扩展验 H3：在 1a 有增益的前提下，做最小页面注入与一段译文缓存。原第 1 阶段的其余内容归入 1b。

### 3.2 需要一个独立来源的 held-out 种子集

第 9 节正确指出"22 个预选仓库、20 道开发题的正例来自候选池，不能证明开放检索"，但没有给替代方案。缺少与开发无关的评估集，E1 只能报案例，不能报召回下限。

建议：从独立来源抽样。HelloGitHub 月刊（[521xueweihan/HelloGitHub](https://github.com/521xueweihan/HelloGitHub)）用中文介绍开源项目，其中相当一部分仓库 README 仅中文。按期号抽样，筛出"README 仅中文"的仓库，与其中文介绍一起构成种子集，只用于评估、不用于开发。构造步骤见 E1 协议第 3 节。同理可为 en→zh 方向反向构造（英文介绍、中文查询）。

### 3.3 先量问题有多大

v0.3 没有回答"README 仅中文的仓库有多少"。若在有一定 stars 的仓库中占比很小，en→zh 方向的价值有限；若 zh→en 方向的痛点主要是"不知道英文术语"，那是一个词表或一次模型改写就能解决的薄问题——E9 处理的正是它。

建议：在 1a 之前用半天做一次规模测量。方法见 E1 协议第 2 节：按 star 区间抽样仓库，取 README 前若干字符计算 CJK 字符占比，分为仅中文／双语／英文，按区间报告占比。这项测量本身就是一条可发表的 receipt。

### 3.4 方向不对称，应显式写进计划

- 中文使用者 → 英文项目：阅读痛点已被沉浸式翻译类工具覆盖；检索痛点主要是术语，薄。
- 英文使用者 → 仅中文项目：真空区，无现成工具。但发起人只能自测前一方向，H7 已承认。

这是一个战略张力：能自测的方向差异化弱，差异化强的方向自己测不了。建议在 v0.4 第 1 节明确选择切入方向，而不是"双向"并列；若仍选双向，写明英文使用者反馈的获取路径与时间点。

### 3.5 对照组具名

- H4 忠实翻译：对照不应是"普通网页翻译"（浏览器内置整页翻译），而应是沉浸式翻译的双语对照模式；后者是目标使用者实际在用的工具。对照选弱，增益会被高估。
- H2 无目标发现：对照加 GitHub Explore／Trending，以及 HelloGitHub 月刊这种人工策展。
- H1 跨语言搜索：对照保持 v0.3 的三组（原生搜索、译词搜索、本方案），并加"支持联网的通用 AI 助手"作为强对照，v0.3 第 5 节已提到，E1 协议中落实为固定组。

### 3.6 评估记录机器可读

v0.3 第 10 节的记录模板是文字表格。建议每次实验的候选记录用结构化文件（JSONL 或 YAML）保存，字段见 E1 协议第 5 节；文字记录写解读。这样"只有某一路径找到"之类的统计不靠人工数。

## 4 工程前置（摘要）

详见 [工程前置检查](../engineering/prerequisites.md)。写扩展前必须过的四项：

1. GitHub Search API 配额：认证 30 次／分钟、未认证 10 次／分钟，单查询最多 1,000 条，`in:readme` 明显慢。每次搜索改写为 2–4 个查询很快撞限。v0.3 说"若额度不足再评估用户自备 GitHub 凭据"；判断是大概率需要，建议直接按需要 PAT 设计，未配置时降级为只做原生查询。
2. 中文查询实测：GitHub 仓库搜索对 CJK 查询与 `in:readme` 的召回需要实测，方法见 E1 协议第 4 节。这是 H1 的技术前置，一小时能完成。
3. GitHub 页面导航：GitHub 使用 Turbo 导航，不整页刷新，content script 需要监听导航事件而不是只在 `DOMContentLoaded` 注入。[Refined GitHub](https://github.com/refined-github/refined-github)（MIT）是现成参考，选择器失效的处理方式也值得借鉴。
4. 模型接入不硬编码 MiniMax：第 8 节的端点核对无误（`https://api.minimax.cn/v1`、`MiniMax-M3`，2026-09-17 复核），但配置面应是 base_url + model + key 的 OpenAI 兼容三元组，MiniMax 是发起人的第一个实例。这样 DeepSeek、OpenAI、本地 Ollama 都能接，Ollama 还能让试用者真正零费用。见 [决策 0002](../decisions/0002-model-endpoint-config.md)。
