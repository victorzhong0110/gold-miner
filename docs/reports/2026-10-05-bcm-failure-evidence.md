# 2026-10-05：B/C/M 模型失败证据缺失（已修）

起因是复核 main 上已记录的 E1 A/B/C/M 实跑时，发现一处**失败记录无法诊断**的缺口。
本记录说明缺口是什么、修了什么、以及对已完成的运行有没有影响。

## 1. 缺口

`runs/2026-10-04-bcm-minimax/generation.jsonl` 里 C 组 `en2zh-eval-03` 的记录是：

```json
{"task_id": "en2zh-eval-03", "arm": "C", "variants": [], "code": "bad_response",
 "notes": "model output JSON parse failed",
 "usage": {"completion_tokens": 232, "reasoning_tokens": 171, "total_tokens": 775}}
```

模型确实返回了内容（232 个 completion token，其中 171 是思考），
但**原文没有被记录**。于是无法判断失败原因是哪一种：

- JSON 外面裹了解释性散文
- 返回的键名不是 `zh` / `en`（schema 不匹配）
- 是拒绝或道歉
- 输出被截断，JSON 没闭合

这四条的处理方式完全不同，但记录里没有任何信息能区分它们。
协议又禁止把失败项重跑进同一批次，所以证据只有第一次机会。

## 2. 同一仓库里 D 组已经做对了

`e1_d_assistant.py` 对同类失败已经留了证据：

| 位置 | 记录字段 |
|---|---|
| `e1_d_assistant.py:633` | `error_excerpt` |
| `e1_d_assistant.py:648` | `error_excerpt`（响应体，限 500 字符） |
| `e1_d_assistant.py:1361` | `answer_text` |
| `e1_d_assistant.py:1369-1371` | `raw_output_sha256`、`raw_output_chars`、`think_present`、`raw_output`（限 16000 字符） |

也就是说**同一类失败在 D 组可诊断、在 B/C/M 组不可诊断**。本轮不是发明新规矩，
是把 D 组已有的做法补到 B/C/M 路径上。

## 3. 修了两件事

### 3.1 失败时保存模型原文

`QueryClientError` 增加 `raw_output` / `answer_text`，失败行按 D 组同样的字段落盘
（`raw_output_sha256`、`raw_output_chars`、`think_present`、`answer_text`、限长的 `raw_output`）。
原文经 `secret_scrub.redact` 脱敏，避免把 key 写进提交记录。

**不改变任何解析行为**，所以不影响已完成的 `2026-10-04-bcm-minimax` 运行的有效性。
成功路径不写这些字段，成功记录不会变大。

新增 `scripts/secret_scrub.py` 供新的记录写入方使用。`e1_d_assistant.py` 保持原样
**故意不动**——它的输出已经落盘并被 PR15 审查过，改它有让运行记录自相矛盾的风险。

### 3.2 顺带发现：解析器会把散文里的示例当成真查询（**污染路径未堵**，见文末更正）

改的过程中发现 `_extract_json_object` 用 `find("{")` / `rfind("}")` 取 JSON。
对于**只有一个**花括号组的回复没问题，但当模型同时给出示例和答案时：

```
输入：Example: {"zh":["demo"]} and my answer: {"zh":["报表生成器"]}
```

`find("{")` 命中第一个、`rfind("}")` 命中最后一个，切出来的是
`{"zh":["demo"]} and my answer: {"zh":["报表生成器"]}`，解析失败——
或者在只有一个示例组时，**直接把示例里的 `"demo"` 当成真实查询记进候选集，
不留任何痕迹**。

C 组提示词明确禁止输出解释和前言，所以合规回复不会命中这个问题。
但「示例被当成真查询」比「解析失败」更危险：它不会报错，
只会安静地往实验里塞一条谁也说不清来源的候选。

改为数出所有**顶层平衡**的花括号组（跳过字符串内的括号）：正好一个就用它，
多于一个就明确报 `ambiguous_model_output` 并拒绝猜。合规输出行为不变。

> ### ⚠️ 2026-10-05 自审更正：本节改动是**诊断改进**，不是「堵住污染」
>
> 我最初把这处改动描述成「修掉了示例被当成真查询的污染」。**这是夸大。**
> 70 例旧/新实现对照实测：**accept/reject 判定 100% 一致**，只改变了错误码。
>
> | 输入 | 旧 | 新 |
> |---|---|---|
> | `Example: {"zh":["demo"]} -> your answer` | **接受，记为 `["demo"]`** | **接受，记为 `["demo"]`** |
> | `{"zh":["demo"]} and my answer: {"zh":["报表"]}` | 拒绝 `bad_response` | 拒绝 `ambiguous_model_output` |
>
> 也就是说：**「只有示例、没有真答案」那条污染路径，改动前后一样敞开。**
> 真正的收益是失败原因从「无法解析」细化为「有多个对象、无法判断哪个是答案」，
> 以及**零回归**（70/70 一致）。
>
> 剩下那个洞刻意不堵：要区分「散文裹着真答案」与「只有示例」必须读句子意图，
> 而本会话已经在这件事上错過两次（材料检查把「本步不要写」读成允许；
> 查询长度探针靠截断整句来变长度）。真正有效的防线是 C 组提示词已禁止散文。
>
> 该路径已由 `test_query_generation.KnownOpenPathsTests` 钉在 suite 里，
> 明确标注为**已知未修**。详见
> [2026-10-05-self-review.md](2026-10-05-self-review.md)。

## 4. 对已完成运行的影响：审计后确认没有

改完之后回头审计已记录的 `2026-10-04-bcm-minimax` 全部 60 条生成记录，
按占位词、JSON 标点、超长、散文特征四个特征扫 40 条 C 组变体：

- **未发现任何散文污染**。6 条初筛命中全是误报：
  `zh2en-eval-09` 的 4 条含 "todo"——那是待办清单应用的正常查询，不是占位符；
  2 条「超长」是 B 组对长英文原句的忠实翻译，符合 B 组定义。
- C 组变体全部是正常检索词（如 `桌面 todo 同步 提醒`、`alipay bill csv parser`）。

**结论：`2026-10-04-bcm-minimax` 和 `2026-10-04-d-minimax` 两个运行的数据没有被这个缺陷污染。**
本轮改动是面向未来的防护，不是对既有结论的翻案。

需要说明的边界：`en2zh-eval-03` C 组那一题的**具体**失败原因仍然不可知——
原文当时就没保存，任何事后推断都是猜测。本记录不猜。
