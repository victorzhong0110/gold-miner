# E1 首轮判定口径 v1（W1 固定，未运行）

对应 [E1 协议](protocol.md)第 4–6 节、[v0.4](../../docs/plan/v0.4.md)第 7 节。状态：已记录、未运行。运行后不改本批口径；调参另开批次。

## 1 检查窗口

- 合并前：每条 GitHub 查询取前 30，不额外翻页（见 `run-settings.json`）。
- 合并后：固定排序并截断为前 30；保留原始位置与各路候选来源。
- 人工判定窗口：首轮统一检查各组前 5 个候选；预算相同。后续扩大到前 10 时另开批次。
- 已知目标诊断另算命中@30，不要求读完 30 个。
- 所有组候选先规范地址（`scripts/github_search.py:canonical`）、去重，合并后隐藏组名做内容核对；原始排名保留。

## 2 逐候选字段（与 `schemas/judgments.schema.json` 一致）

- `purpose_fit`：`yes` 符合 / `partial` 部分符合 / `no` 不符合。依据任务 `need` 句，不含仓库名先验。
- `hard_conditions`：`satisfied` 满足 / `conflict` 冲突 / `unknown` 未知。未知不能算满足。
- `kind`：`tool` 工具 / `library` 库 / `tutorial` 教程 / `list` 清单 / `mirror` 镜像 / `other` 其他。学习实现或示例按学习目的评价归入 `tutorial` 或 `other` 并在 `notes` 说明，不自动排除或通过。
- `novel_to_judge`：`yes` / `no`。是否首次见到；回忆不确定时如实记，不补造。
- `worth_following`：是否值得继续看。必填理由 `reason`：原话或明确标记的技术判断；真实使用者价值判断与技术判断分列。
- `judge` / `judged_at`：判定人标识与 RFC 3339 时间。同一人构题和判断时照实披露；未实现盲测不写“盲测完成”。
- `notes`：阅读受影响（工具失效）、原文定位、项目与子能力线索（同仓库不同能力可另记线索，但项目数按规范仓库去重）。

## 3 else 规则

- 拿不到匹配字段记 `unknown`，不按标题相似度补造（候选记录侧，见协议第 5 节）。
- 仓库不存在、迁移、限流/超时与不相关结果分开统计。
- 开放任务作者不先看种子答案；由项目介绍反推的查询只作已知目标题并标注偏差。
- 小样本存在熟悉效应、选择偏差与非盲判断时在报告中直接写明。

## 4 指标解释边界（报告用，不预填结论）

- 已知目标命中@30：种子任务中指定目标进入该组前 30 的比例；不是总体召回率。
- 各组独有合适候选：在相同检查窗口内仅该组发现、用途符合、无已知硬冲突；条件未知单列；不表示别的路径永远找不到。
- 有价值的新发现：原本不知道、能说明用途或学习点、愿意继续探索；保留判断者身份；不只按点击或模型打分计数。
- 前 K 适合度：报用途匹配及条件已满足/未知分项；不把用途匹配当成可直接使用。
- A→C 为整体辅助效果；M→C 才接近相同预算下的语言扩展贡献；B→C 判断复杂程度是否值得。
