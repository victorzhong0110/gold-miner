## 执行顺序和条件分支

1. 先确认唯一写入负责人、平台/会话和工作区，再领取一个明确子任务或工作包。
2. 优先结清既有 PR #2 的三项审查问题、补实际安装验证；它们属于既有实现收尾，归 WP3/4，不代表全面展开后续功能。
3. WP1 → WP2 完成材料、真实执行与首轮决策。E1、E2、E3分别判断，某一路失败不自动否决其他路径。
4. WP3/4复用现有扩展；扩大功能依据 WP2 证据。人工候选有用只支持试自动化，自动获取和排序仍需分别测。
5. WP5前完成许可决定（WP6-02可提前），随后试用、复用和持续使用；WP6复测与发布取决于实际证据。
6. 现成翻译够用就不自建；没有重复调用收益就不做公共托管；E9只在诊断需要时运行；商店上架是另行授权的可选项。
7. 搜索与自动发现均无收益时，保留一次有依据的修正复测，之后可缩小或暂停，不为凑齐日程扩功能。

## 规范、授权和状态语义

本目录提供完整任务分解和统一入口，不覆盖实验的详细合同。main 的 [AGENTS](../../AGENTS.md)、[v0.4](../plan/v0.4.md) 与 PR #2 分支的新闸门存在历史差异；WP1-02负责显式对齐。PR #2 的 v0.5 是分支候选规范，不能悄悄宣称已进入 main。规范变更由规划/评审方维护，执行代理不得自行放宽验收；计划登记不能代替用户对扩展范围、合并、发布或许可的决定。

所有任务分别报告五层状态：实现了什么、验证了什么、提交到哪里、合并了什么、实际验收了什么。fixture通过不是live通过，CI通过不是浏览器或真人体验通过，提交不等于合并，安装成功不等于发现效果有效。

每包只有一个写入负责人；其他代理只读审查。可独立准备的事项列在依赖里，不因此自动并行派发。缺少 API key 不等于不能实现可注入客户端；缺少浏览器环境与缺少真人反馈分开记录。远端历史证据与本轮实测分开。
