# 0004 E1 模型与 D 组预算

状态：已决定。决定日期：2026-10-04。决定人：发起人 Victor。

## 决定

1. E1 以及其余模型调用只使用 MiniMax。具体模型为 `MiniMax-M3`。
2. 接入方式为 OpenAI 兼容接口。大陆平台基址为 `https://api.minimax.cn/v1`；`https://api.minimaxi.com/v1` 同样可用。密钥只来自环境变量，不写入仓库。
3. `MiniMax-M3` 是推理模型。思考会计入输出长度。D 组单次请求的输出上限冻结为 8192 token。
4. D 组预算不设任务条数上限，按协议跑满 `eval.batch_1`（20 条开放题）。不把结果并进未同时运行的组的全量平均。
5. MiniMax 用量配额约每 5 小时重置。遇到配额或频率限制时，停在尚未完成的任务上，记录任务标识后等待重置再继续。看不见的费用写「未知」。

## D 组怎么调用

协议第 3 节把 D 定义为联网助手强对照，不是把 B/C/M 的查询生成换一个名字。

2026-10-04 核对的大陆官方文档写明：服务端联网工具 `web_search` 不在 Chat Completions 上提供，而在同一基址的 OpenAI Responses API（`POST /v1/responses`，工具类型 `web_search`）。本批 D 使用该接口和该工具，模型仍是 `MiniMax-M3`，密钥与基址与上面的决定相同。Chat Completions 的 `<think>` 行为不作为本批 D 的调用面。

不给模型接 GitHub Search 作为客户端工具。仓库是否存在，由运行脚本在模型给出名单之后用 GitHub API 核对；不存在的记为幻觉。

## 本决定没有包含的事

- B/C/M 的实跑。查询生成脚本里的 `max_tokens` 仍是 256，对 `MiniMax-M3` 已知不够；在真正跑 B/C/M 之前要单独改，本决定不把那一次改动算成已经跑过。
- 人工盲判、用途适合度和「值得继续看」。
- 可见账单金额。响应里没有费用字段时记未知，不按 token 折算价钱。
